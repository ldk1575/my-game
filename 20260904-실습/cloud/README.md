# 내 Todo 앱 — 길 B (클라우드)

AI에이전트 2기 · 2026-09-04 노드「데이터베이스」실습

**링크 하나만 주면 여러 사람이 각자 자기 목록을 쓰는** Todo 앱.
화면은 GitHub Pages, 데이터는 Supabase(무료).

## 길 A와 무엇이 다른가

| | 길 A (로컬) | 길 B (클라우드) |
|---|---|---|
| 데이터 | 내 PC의 `todo.db` 파일 | Supabase Postgres |
| 백엔드 서버 | `server.js` (내 PC) | **없음** — 브라우저가 Supabase를 직접 부름 |
| 남에게 보여주기 | 안 됨 | **링크로 됨** |
| 여러 사람 | 개념 없음 | 각자 자기 목록 (익명 로그인 + RLS) |
| 안전장치 위치 | 서버 코드 | **DB 정책(RLS)** |

## 실행

**배포된 링크** — 이걸 남에게 주면 됩니다.

```
https://ldk1575.github.io/my-game/20260904-실습/cloud/
```

**배포 전 로컬 확인**


## 여러 사람이 같은 링크를 쓰는 원리

```
사람 A가 링크 열기 → Supabase가 A에게 고유 user_id 발급 (로그인 화면 없음)
                     A가 쓴 행에 user_id = A 가 박힌다
사람 B가 링크 열기 → B에게 다른 user_id 발급
```

그리고 정책이 대상을 '내 것'으로 한정합니다.

```sql
create policy "todos: 내 것만" on public.todos
  for all to authenticated
  using      ( auth.uid() = user_id )   -- 읽기·수정·삭제 대상
  with check ( auth.uid() = user_id );  -- 남의 이름으로 넣기 차단
```

`user_id` 열의 기본값이 `auth.uid()` 라서 **클라이언트가 보내지 않아도 자동으로 박힙니다.**

### 어제 프로젝트(ai-collab-mbti)와 다른 판단

어제는 **읽기 정책을 아예 만들지 않는** 방법으로 막았습니다. 쓰고 집계 숫자만 돌려받는
앱이었으니 그게 가능했죠. Todo 앱은 내가 쓴 걸 내가 다시 읽어야 목록이 뜨므로,
**읽기를 허용하되 대상을 내 것으로 한정**하는 방식으로 바꿨습니다.

함수에서도 정반대 선택을 했습니다.

| 함수 | security | 왜 |
|---|---|---|
| `get_stats` (어제) | **definer** | RLS를 우회해 **원본은 숨기고 숫자만** 계산해 돌려주려고 |
| `add_todo` (오늘) | **invoker**(기본) | 부른 사람 권한으로 돌아야 `auth.uid()`와 RLS가 적용됨. definer로 쓰면 **남의 이름으로도 쓸 수 있어 위험** |

### 트랜잭션은 왜 함수로 옮겼나

길 A에서는 `BEGIN`/`COMMIT`으로 묶었습니다 — `todos` 한 줄 + `tags` 신규분 + `todo_tags` 여러 줄.
그런데 브라우저에서 REST로 부르면 **요청이 3~4번으로 쪼개져** 중간 실패 시 태그 없는 할 일이나
주인 없는 연결 줄이 남습니다. **클라이언트에서는 트랜잭션을 걸 수 없습니다.**

→ `add_todo` 함수로 만들면 **본문 전체가 하나의 트랜잭션**이 됩니다. 어제 `get_stats`를 만든 것과 같은 패턴입니다.

## 공격 테스트 결과 (`node verify-rls.mjs` · 2026-09-04)

익명 사용자 A·B를 실제로 만들어 서로의 데이터를 노려봤습니다. **13 PASS / 0 FAIL.**

| 시도 | 결과 |
|---|---|
| A가 자기 할 일 조회 | ✅ 1건 — 태그까지 정상 |
| **B가 A의 할 일 조회** | ✅ **0건** — RLS가 행을 숨김 |
| **B가 A의 할 일 삭제** | ✅ **0건 삭제** — HTTP 200이지만 데이터 그대로 |
| **B가 A의 할 일 수정** | ✅ **0건 수정** |
| **B가 A의 이름으로 삽입** | ✅ **HTTP 403** — `new row violates row-level security policy` |
| 로그인 안 한 anon 조회 | ✅ 0건 |
| 빈 제목 / 300자 제목 | ✅ **HTTP 400** — `todos_title_len` 제약 |
| `Robert'); DROP TABLE todos;--` | ✅ **제목으로만 저장**, `todos` 표 생존 |
| A가 자기 것 삭제 | ✅ 삭제됨 (연결 표는 CASCADE) |

RLS는 **에러를 내는 대신 대상 행을 아예 안 보이게** 만듭니다. 그래서 삭제·수정이
"성공(200)했지만 0건"으로 돌아옵니다. 어제 프로젝트에서 관찰한 것과 같은 현상입니다.

## 알고 써야 하는 한계

| 한계 | 왜 | 대책 |
|---|---|---|
| **기기·브라우저 바뀌면 새 사람** | 세션이 그 브라우저 `localStorage`에만 있음. 시크릿창도 새 사람 | 실습·데모엔 문제 없음. 넘으려면 이메일/소셜 로그인 |
| **브라우저 데이터 지우면 접근 불가** | 그 `user_id`로 다시 로그인할 방법이 없음 → 행은 남고 고아가 됨 | 위 테스트에서 실제로 2건이 고아가 됐다. SQL Editor에서 정리 가능 |
| **계정을 무한히 만들 수 있음** | 누구나 익명 로그인 가능 → MAU 부풀리기 | 수업 동료 몇 명이면 무료 한도(MAU 5만) 안. **공개적으로 뿌릴 거면 CAPTCHA 필요** |
| **행을 무한히 넣기** | 500MB 한도를 채울 수 있음 | 트리거로 막음 — 한 사람당 할 일 200개 / 태그 50개 |

**⚠️ 블로그 `iframe`에 넣으면 깨집니다.** 다른 도메인의 iframe 안에서는 브라우저가 스토리지를
분리·차단해서(Safari ITP, Chrome 서드파티 스토리지 정책) 매번 새 익명 사용자가 됩니다.
**독립 링크로 주셔야 합니다.** 블로그에는 링크를 걸어두세요.

### 공유할 때 — 카카오톡 인앱 브라우저 주의

실기기(Android)로 확인하다 발견했습니다. **카카오톡으로 링크를 보내면 받는 사람은 카톡
인앱 브라우저에서 엽니다.** 인앱 브라우저는 앱을 닫을 때 저장소를 비우는 경우가 많아,
다시 열면 **새 사용자가 되어 목록이 비어 보일 수 있습니다.**

한국에서 링크를 공유하는 가장 흔한 경로가 카카오톡이니, 링크와 함께 이 안내를 보내세요.

> "목록을 계속 쓰시려면 `⋮` → **다른 브라우저로 열기** 로 열어주세요."

기본 브라우저(Chrome·Safari)에서 열면 저장소가 유지됩니다.

**iframe · 인앱 브라우저 · 시크릿창 · iOS Safari 7일 만료가 모두 같은 이유**입니다 —
익명 세션이 `localStorage`에 있어서, 저장소가 분리되거나 지워지는 환경에서는 신분이
유지되지 않습니다. 기기를 넘어 유지하려면 이메일/소셜 로그인이 필요합니다.

## 키에 대하여

`index.html`에 `publishable`(anon) 키가 그대로 들어 있습니다. **이 키는 원래 공개되는 용도**입니다.
`secret` / `service_role` 키는 **절대 넣지 않았습니다** — 그건 RLS를 우회하는 키라 노출되면 DB가 전부 열립니다.

> 안전을 담보하는 것은 키가 아니라 정책입니다.
