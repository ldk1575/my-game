# 작업 기록 — 판단한 것과 고친 것을 순서대로

AI에이전트 2기 · 2026-09-04 노드「데이터베이스」실습

결과물만 보면 매끄러워 보이지만, 실제로는 **막히고 고친 지점이 열세 군데** 있었다.
그 과정을 순서대로 남긴다. 잘 된 것보다 **틀렸다가 고친 것**이 배운 것에 가깝다.

## 0. 시작 — 노드 실습을 그대로 따르기로

노드 문서의 순서를 그대로 밟았다.

```
1부 PRD 쓰기 → DB 구조 설계받기 → 2부 길 A(로컬) → 3부 길 B(클라우드)
```

내가 넣기로 한 기능은 **마감일 · 태그(카테고리) · 오늘 할 일만 보기** 셋.
태그를 고른 이유가 있다 — 오늘 배운 **N:M 관계와 연결 표**를 직접 만들어 봐야 했기 때문이다.

## 1. 노드 문서의 1번 트러블슈팅을 통째로 없앤 판단

노드 트러블슈팅 표의 첫 줄이 이거였다.

> `npm install`에서 better-sqlite3 빌드 에러(node-gyp) — 네이티브 모듈이라 빌드 도구가 필요

`node -v` 를 찍어보니 **v24.19.0**. Node 22부터 SQLite가 런타임에 내장(`node:sqlite`)됐다는 걸 확인하고
플래그 없이 되는지 먼저 시험했다.

```
node:sqlite OK -> { a: 7 }
```

**됐다.** 그래서 `better-sqlite3`를 쓰지 않았고, 결과적으로 **의존성 0개 · `npm install` 불필요**가 됐다.
가장 흔한 실습 실패 지점이 사라졌다.

**배운 것** — 문서가 제시한 도구를 그대로 쓰기 전에, 내 환경에서 더 간단한 길이 있는지 확인해 볼 만하다.

## 3. "추가가 안 된다"고 착각한 일

할 일 4건을 넣었는데 화면이 *"아직 할 일이 없습니다"* 였다. DB 문제인가 싶었지만
서버 로그에 에러가 없었다. 네트워크 요청을 확인해 보니

```
POST /api/todos → 201 Created   × 4건
GET  /api/todos → 200 OK
```

**저장은 다 되어 있었다.** 응답 본문까지 열어 보니 4건이 정확히 들어 있었다.
화면 캡처가 마지막 목록 갱신보다 **먼저** 찍힌 것이었다.

**배운 것** — "화면에 안 보인다"와 "저장이 안 됐다"는 다른 문제다.
증상을 보고 원인을 단정하기 전에 **어느 층에서 끊겼는지** 확인해야 한다.
로그 → 네트워크 → 응답 본문 순으로 좁혀 들어가면 금방 나온다.

## 4. "색인 걸었다"로 끝내지 않고 실제로 타는지 확인

색인을 세 개 걸었지만, 정말 타는지는 별개 문제다. `EXPLAIN QUERY PLAN`을 돌렸다.

```
SEARCH todos USING INDEX idx_todos_due (due_date=?)
```

`SCAN todos`(처음부터 전부 훑기)가 아니라 `SEARCH ... USING INDEX`가 나왔다. **탄다.**

**배운 것** — 색인은 걸어 두는 것과 쓰이는 것이 다르다. 확인 방법이 있으면 확인해야 한다.

## 5. 삭제하다 발견한 CASCADE의 동작

SQL 주입 테스트로 넣은 항목을 지웠더니 태그 집계가 이렇게 됐다.

```
#긴급 1  #발표 1  #실습 1  #정리 1  #보안테스트 0
```

`#보안테스트`가 **0으로 남았다.** `ON DELETE CASCADE`가 `todo_tags` 연결 줄만 지우고
`tags` 행은 살린 것이다. 정규화가 어떻게 동작하는지가 눈에 보이는 장면이었다.

## 6. 어제 방식이 Todo에 안 맞는다는 걸 발견 (길 B 설계)

길 B는 어제 제출한 프로젝트(`ai-collab-mbti`) 방식을 그대로 쓰려고 했다.
정적 HTML + Supabase REST 직접 호출 + publishable 키 + 안전장치는 DB에.

그런데 어제 `supabase-setup.sql`을 다시 읽다가 이 줄에서 멈췄다.

```sql
-- 읽기(select) 정책은 만들지 않는다.
-- → 브라우저에서 원본 결과 목록을 절대 꺼내볼 수 없다.
```

**어제 앱의 안전은 "읽기를 아예 막는 것"에 크게 의존했다.** 쓰고 집계 숫자만 돌려받으면
끝나는 앱이었으니 가능한 설계였다.

**Todo 앱은 정반대다.** 내가 쓴 걸 내가 다시 읽어야 목록이 뜬다. 그런데 로그인이 없으면
"내 것"을 구분할 방법이 없다. 어제 방식을 그대로 붙이면 —

| 필요 기능 | 줘야 하는 권한 | 결과 |
|---|---|---|
| 목록 보기 | anon에게 `select` | 누구나 남의 할 일을 다 본다 |
| 완료 토글 | anon에게 `update` | 누구나 남의 할 일을 고친다 |
| 삭제 | anon에게 `delete` | 누구나 남의 할 일을 지운다 |

**공용 낙서장이 된다.** 링크를 뿌리면 누가 다 지울 수 있다.

→ 그 자리를 **Supabase 익명 로그인 + `auth.uid() = user_id` RLS**로 채웠다.
로그인 화면 없이 브라우저마다 고유 id를 받고, 정책이 대상을 내 것으로 한정한다.

**직접 만드는 방법도 검토했다가 버렸다** — `owner_token`을 localStorage에 두고 필터하는 방식.
노드 원칙("인증은 직접 만들지 마라")에 어긋나고, 무엇보다 **RLS로 막을 수 없다.**
클라이언트가 아무 토큰이나 넣어 조회할 수 있어 실제로 안전하지 않다.

**배운 것** — 잘 만든 설계를 그대로 가져오는 것보다, **그 설계가 무엇에 의존했는지**를
아는 게 중요하다. 전제가 바뀌면 같은 설계가 정반대 결과를 낸다.

## 7. 클라이언트에서는 트랜잭션을 걸 수 없다

길 A에서는 할 일 추가를 이렇게 묶었다.

```js
db.exec('BEGIN');   // todos 1줄 + tags 신규분 + todo_tags 여러 줄
db.exec('COMMIT');  // 전부 되거나 전부 안 되거나
```

프론트엔드를 설계하다 알았다 — **브라우저에서 REST로 부르면 요청이 3~4번으로 쪼개진다.**
중간에 실패하면 태그 없는 할 일이나 주인 없는 연결 줄이 남는다. 오늘 배운 원자성이 깨진다.

→ **`add_todo` 라는 Postgres 함수(RPC)로 옮겼다.** 함수 본문은 자동으로 하나의 트랜잭션이다.
어제 `get_stats`를 만든 것과 같은 패턴이다.

그리고 여기서 **어제와 정반대 판단**을 했다.

| 함수 | security | 왜 |
|---|---|---|
| `get_stats` (어제) | **definer** | RLS를 우회해 원본은 숨기고 숫자만 돌려주려고 |
| `add_todo` (오늘) | **invoker**(기본) | 부른 사람 권한으로 돌아야 `auth.uid()`와 RLS가 적용됨 |

`add_todo`에 `definer`를 쓰면 **RLS를 우회해 남의 이름으로도 쓸 수 있게 되어 위험하다.**
같은 프로젝트 안에서 두 함수가 반대 선택을 한 이유가 이것이다.

## 8. SQL 문법 에러 — 배열 슬라이스는 변수에만

`supabase-setup.sql`을 실행했더니 실패했다.

```
ERROR: 42601: syntax error at or near "["
LINE 234:   foreach v_name in array coalesce(p_tags, '{}'::text[])[1:5]
                                                                  ^
```

PostgreSQL에서 배열 슬라이스 `[a:b]`는 **변수·열에만** 붙는다. 함수 호출 결과에 바로 붙일 수 없다.

```sql
-- 안 됨
foreach v_name in array coalesce(p_tags, '{}'::text[])[1:5]

-- 됨 — 변수에 담고 나서 자른다
v_tags := coalesce(p_tags, '{}'::text[]);
v_tags := v_tags[1:5];
foreach v_name in array v_tags
```

**배운 것** — 에러 메시지가 `at or near "["` 로 위치를 정확히 가리켰다.
메시지를 끝까지 읽으면 대개 답이 그 안에 있다.

그리고 **앞부분이 이미 만들어졌을까 걱정하지 않아도 됐다** — SQL Editor는 스크립트 전체를
한 트랜잭션으로 돌리므로 실패 시 앞의 것도 전부 취소된다. 오늘 배운 원자성이 여기서도 작동했다.

## 9. 검증하다 발견한 anon 권한 구멍

정책을 넣고 끝내지 않고, **익명 사용자 A·B를 실제로 만들어 서로의 데이터를 노려보는**
스크립트(`cloud/verify-rls.mjs`)를 짰다. 어제 README의 공격 테스트 표와 같은 생각이다.

**13 PASS / 0 FAIL** 이 나왔지만, 한 항목의 결과가 예상과 달랐다.

```
8) 로그인 안 한 anon 으로 조회
   기대: HTTP 403 (권한 없음)
   실제: HTTP 200 + 0건
```

`grant`를 `authenticated`에게만 줬으니 권한 자체가 없어야 했다. 그런데 200이 온 것은
**프로젝트에 `anon` 기본 권한이 이미 있어서** 테이블 접근은 되고 RLS가 행을 전부 막은 상태였다는 뜻이다.

결과는 안전하지만, **나중에 실수로 anon 정책이 하나 추가되면 그 순간 열린다.**
그래서 권한 자체를 회수하는 구문을 추가했다.

```sql
revoke all on public.todos     from anon;
revoke all on public.tags      from anon;
revoke all on public.todo_tags from anon;
```

**배운 것** — 통과했더라도 **왜 통과했는지**를 보면 구멍이 보인다.
"막혔다"와 "의도한 방식으로 막혔다"는 다르다.

## 10. 어제와 달리 iframe에 넣을 수 없다는 발견

어제는 GitHub Pages에 올린 뒤 블로그에 `iframe`으로 삽입했다. 이번에는 그러면 **깨진다.**

익명 로그인 세션은 브라우저 `localStorage`에 저장된다. 그런데 다른 도메인의 iframe 안에서는
브라우저가 스토리지를 분리·차단한다(Safari ITP, Chrome 서드파티 스토리지 정책).
그러면 열 때마다 세션이 사라져 **매번 새 익명 사용자**가 되고, 방금 쓴 할 일이 다음 방문에 안 보인다.

→ **독립 링크로 공유**하고, 블로그에는 링크만 걸기로 했다.

로컬 원본에는 그대로 남겨 뒀다. **되돌리기 어려운 쪽을 피하는 방향으로** 판단했다.

## 12. 데모하다 관찰한 고아 데이터

"다른 사람이 열면 어떻게 되나"를 확인하려고 세션을 지우고 다시 열었다.

```
익명 ID :  4a2614f4…  →  0bffae9e…
목록    :  2건         →  0건
```

의도한 대로 **앞 사용자의 할 일이 완전히 안 보였다.** 동시에 한계도 드러났다 —
그 2건은 **DB에 남아 있지만 이제 아무도 접근할 수 없는 고아 데이터**가 됐다.
익명 로그인의 대가다. 브라우저 데이터를 지우면 이렇게 된다.

## 13. 실기기에서 확인하다 발견한 것 — 인앱 브라우저

배포하고 끝내지 않고 **휴대폰으로 직접 열어봤다.** 그 전에 375px 에뮬레이션으로 재보니
기능은 다 되는데 **손가락으로 쓰기가 불편했다.**

| 항목 | 처음 | 고친 뒤 |
|---|---|---|
| 제목 입력칸 | **143px** (마감일칸 150px보다 좁음) | 313px |
| 체크박스 | **20×20** (권장 44) | 24×24 + 누를 범위 44px |
| 삭제 버튼 | **25×22** | 27×26 + 누를 범위 44px |

제목과 마감일을 한 줄에 나란히 둔 게 원인이었다. 480px 이하에서는 위아래로 쌓게 바꿨다.
터치 타겟은 **보이는 크기를 키우지 않고** 투명한 `::before` 로 누를 영역만 넓혔다.

```css
.chk::before, .del::before{ content:""; position:absolute; inset:-11px; }
```

`elementFromPoint` 로 히트테스트해서 중심에서 상하좌우 ±20px 이 모두 눌리는 것을 확인했다.

### 그리고 실기기에서만 보인 것

에뮬레이션에서는 다크 모드로 나왔는데, 실기기는 라이트 모드였다.
`prefers-color-scheme` 대응이 양쪽 다 동작하는 것을 **실기기에서야** 확인했다.

더 중요한 건 이쪽이다 — 열어본 곳이 **카카오톡 인앱 브라우저**였다.
주소창에 `가가` 버튼이 있는 그 화면이다.

**인앱 브라우저는 앱을 닫을 때 저장소를 비우는 경우가 많다.** 익명 세션이 `localStorage` 에
있으니, 카톡에서 링크를 다시 열면 **새 사용자가 되어 목록이 비어 보일 수 있다.**

이게 실전에서 중요한 이유 — **한국에서 링크를 공유하는 가장 흔한 경로가 카카오톡이다.**
링크를 보내면 받는 사람도 인앱 브라우저에서 연다. 앱은 잘 만들었는데 정작
공유 경로에서 신분이 유지되지 않는 상황이 된다.

→ 링크를 공유할 때 안내를 함께 보내기로 했다.

> "목록을 계속 쓰시려면 `⋮` → **다른 브라우저로 열기** 로 열어주세요."

**배운 것** — 10번(iframe 금지)과 뿌리가 같다. 익명 세션이 `localStorage` 에 있다는 선택은
**저장소가 분리되거나 지워지는 환경 전부**에 영향을 준다. iframe, 인앱 브라우저,
시크릿창, iOS Safari의 7일 만료가 모두 같은 이유로 걸린다.
설계할 때 "어디에 저장하나"를 정하면 **거기에 딸린 제약이 함께 온다.**

그리고 **에뮬레이션은 실기기를 대체하지 않는다.** 인앱 브라우저는 재보려는 생각조차
못 했던 항목이었다.

## 정리 — 오늘 배운 것이 실제로 쓰인 자리

| 배운 것 | 어디서 실제로 걸렸나 |
|---|---|
| **표로 나누고 관계로 잇기** | 태그를 `todos`에 욱여넣지 않고 `tags` + `todo_tags`로 |
| **N:M은 연결 표로** | 6번 — 태그를 고른 이유 자체가 이걸 만들어 보려는 것이었다 |
| **파라미터화 쿼리** | 모든 쿼리에 `?` 자리표. `Robert'); DROP TABLE todos;--` 를 넣어도 제목으로만 저장 |
| **트랜잭션(원자성)** | 7번 — 클라이언트에서 못 걸어 RPC 함수로 옮겼다. 8번 SQL 실패 때도 이 성질이 작동 |
| **색인** | 4번 — `EXPLAIN`으로 실제로 타는지 확인 |
| **정규화** | 5번 — CASCADE 관찰로 눈에 보였다 |
| **RLS와 최소 권한** | 6·9번 — 정책 설계, 그리고 통과했는데도 구멍을 찾은 것 |
| **"인증은 직접 만들지 마라"** | 6번 — `owner_token` 자작 방식을 검토했다가 버렸다 |
| **덜 모으는 게 안전** | 11번 — 실명을 안 올리는 판단 |
| **무료 티어 함정** | 1주 미사용 정지 · 자동 백업 없음 · 500MB. 트리거로 행 수 상한을 걸었다 |

**가장 오래 남을 것 하나** — 6번이다. 어제 잘 만든 설계를 그대로 가져오려다,
**그 설계가 "읽을 필요가 없는 앱"이라는 전제에 의존했다**는 걸 알았다.
전제가 바뀌면 같은 설계가 정반대 결과를 낸다. 좋은 코드를 베끼는 것보다
**왜 그렇게 만들었는지를 아는 것**이 쓸 수 있는 지식이었다.
